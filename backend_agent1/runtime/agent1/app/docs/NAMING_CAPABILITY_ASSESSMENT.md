## 实际流程和项目基础

1. MinerU 或直接 PDF 文本，加原页/裁图的实际观察，建立本篇证据。
2. 分清研究材料、有限组分、使用实例、盐/电荷、连接方式与用量基准。
3. `prepare_component` 从原文定义、同文上下文、Registry 有限候选或明确标注的系统重述，准备工具名称；保留原文缩写、同义词、来源和歧义。Registry 结果是候选，不能把目录 ID、公式或 expected 当结构求解输出。
4. OPSIN 名称解析与 RDKit 图检查，核对有限组分及对应实际图。PubChem 等仅在确实调用时才是外部证据；解析成功不证明实际聚合产物。
5. 对高分子明确理想重复、局部连接、仅来源或非共价组装的表达。连接未知时，可以采用与原文相容的最可能假设，但不能把假设改写为来源事实；投料量与产物组成分开保存。
6. 同一 Kernel/create_passport/NamingService 生成或检查名称，结合显式命名声明选择结构型、来源型、改性、接枝或共混路线。工具返回的名称要明确保存到当前材料，核对最新依赖状态后 review/finish；封存、采用和界面读取同一版本。

这个流程合理：语言模型负责理解证据和选择假设，程序负责限定图编辑、规则生成与一致性检查。已接入 Registry、Kernel、命名服务、RDKit、OPSIN 和公共查询入口；历史全库尚未自动成为可信求解能力，不能称基础已全部接通。

## 是否相当于 Skill

任务提示协议可以封装为 Skill，便于复用“识别对象—准备组分名—选择命名路线—保留假设—定稿”的方法。但现有功能是提示协议与可执行化学后端的组合，单独一个 Skill 无法保证原子保留、价态、端口、图名一致和不可变版本。

当前 `runner.init_job` 实际复制 `resources/core-prompt.md` 到任务 AGENTS.md。`resources/naming/SKILL.md` 及三个 references 被纳入实现哈希，但没有当前 APP 单独装载 freeze/context 的调用证据；其中“为 GLM 装载”的文字属于已有历史描述。不能把“文件存在”说成命名 Skill 已独立运行。本任务不新增另一套会话、规则或工作流。

## 有收益的提升顺序

| 优先事项 | 可以改善什么 | 何时停止继续扩展 |
|---|---|---|
| 组分名准备、名称采用与依赖复核 | 少输缩写给 OPSIN，减少名称只存在于回执、依赖更新后复核过期等失败 | 多类型正常文献已稳定自动定稿；无需堆提示词或重复查询 |
| 完整重复图到结构型名称 | 通用残基连接、子单元分解、方向与位次；已有 PTh、PEDOT、PDMS 的图名一致候选说明此方向有实际收益 | 仅为单篇论文的特例、只是同义改写、删掉未识别取代基，均不算收益 |
| 改性/接枝/共聚/网络边界 | 区分点功能化与聚合侧链、来源型共聚与唯一序列、局部交联与整网 | 原文根本没有序列、并入比、掺杂量或位点证据时，应保留较宽名称/假设与未知 |
| 严格优选 CRU/PIN | 在有足够证据的范围补 RSSOP 优先级、平局、立构等规则 | 没有独立审核时，不能仅凭 OPSIN 解析、程序回验或 pytest 宣布认证完成 |

上一任务已经把 PTh、PEDOT 和 PDMS 的主要名称提升为完整周期图一致的结构型候选，并为 TMPMT 共聚物补局部连接图；这证明优化能增加结构信息，但不是独立准确率证明。本次命名增量为零，既有未知、旧命名空间及版本保留。
