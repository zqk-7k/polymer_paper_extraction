# 双仓库协作与发布流程

## 仓库职责

| 仓库 | 角色 | 应提交的内容 |
|---|---|---|
| `leexh2333-jpg/polymer_paper_extraction` | 开发上游 | 抽取流程、提示词、数据结构、测试以及通用前后端功能 |
| `zqk-7k/polymer_paper_extraction` | 集成与生产 | 自动合并上游，并保存容器、CI/CD 和服务器部署配置 |

开发者继续在开发上游的 `main` 分支工作。生产仓库每小时检查一次上游，也可以在 Actions 页面手动运行 `Sync development upstream`。

## 自动链路

```text
开发者推送上游 main
        ↓
生产仓库定时拉取并执行 Git merge
        ↓
有冲突：同步失败并停止，不修改线上版本
无冲突：推送生产 main
        ↓
触发 CI：Python 测试、前端测试、两个 Docker 构建检查
        ↓
CI 全部通过后，把同一提交归档并部署到服务器
```

GitHub 使用的合并是真实 Git merge，不是覆盖复制，因此两边提交历史和作者信息都会保留。

## 开发纪律

1. 抽取核心和通用产品功能只在开发上游首发，避免同一文件在两个仓库同时修改。
2. 服务器地址、Docker Compose 和发布脚本只在生产仓库维护。
3. 在生产仓库发现的通用 Bug，应以 PR 或 cherry-pick 形式回送开发上游。
4. 自动合并发生冲突时，线上版本保持不变。人工解决冲突并通过完整 CI 后才能部署。
5. API Key、服务器密码、SSH 私钥和运行结果不得提交到任何仓库。

## 首次统一

当前生产仓库包含开发上游的全部提交，并额外包含在线工具和部署提交。建议将 `web_api/`、`web_portal/` 及其通用测试整理成 PR 回送开发上游；服务器专用的 `deploy/` 和生产 Secrets 继续只保留在生产仓库。
